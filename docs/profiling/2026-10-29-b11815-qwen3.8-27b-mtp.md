# b11815 · Qwen3.8 27B with MTP · 2026-10-29

Two captures of the same benchmark under LlamaWebUI's profiler. Run 1 has the GPU and CUDA timeline only (CPU sampling was requested but recorded nothing). Run 2 adds CPU call stacks ([Run 2](#run-2-cpu-call-stacks)).

**Summary.** During generation the GPU is busy 87–89% of the time. Each step is about 1.6 ms of GPU work followed by a median 0.57–0.65 ms gap while the CPU makes about 27 waits and 10 small copies. That gap is about a quarter of the step and is the clearest target. Run 2's call stacks put most of it in **MTP drafting** and in **copying graph inputs to the GPU**. Drafting makes several small GPU round trips per step. The input copies go through `cudaMemcpyAsync` calls that block the decode thread (14.5% of its samples). Which kernels make up the 1.6 ms is still open (run B in [Next captures](#next-captures)).

## The generation step

Measured over the middle third of the capture (23.1 s of steady generation):

- **3,863 CUDA graph replays, 167 per second.** Replay median **1,601 µs** (p90 24 ms, from the occasional large batch).
- **GPU gap after each replay: median 567 µs** (p90 1,670 µs). Replays cover 86% of the window.

What the CPU does per replay:

| CUDA call | Per replay | Total in window | Median |
|---|---|---|---|
| `cudaStreamSynchronize` | 27.0 | 20.2 s (mostly waiting for the replay itself) | 1 µs |
| `cudaMemcpyAsync` | 10.1 | 0.33 s | 5 µs |
| `cudaLaunchKernel` (outside the graph) | 13.0 | 0.22 s | 3 µs |
| `cudaGraphLaunch` | 1.0 | 0.35 s | 26 µs |

A typical step on the CPU thread is one graph launch, then about a dozen *copy, then wait* pairs:

```
cudaGraphLaunch > cudaMemcpyAsync ×3 > cudaStreamSynchronize ×8
  > cudaMemcpyAsync > cudaStreamSynchronize ×3
  > (cudaMemcpyAsync > cudaStreamSynchronize ×2) ×9
  > cudaMemcpyAsync > cudaStreamSynchronize
```

Copies in the window:

| Direction | Per replay | Common sizes |
|---|---|---|
| Device → host | 2.4 | 40 B, 20,480 B, **4,966,400 B** (649×), 102,400 B |
| Host → device | 7.7 | 20,480 B, 8 B, 102,400 B, 40 B, 4 B |

The graph is rarely rebuilt: 116 `cudaGraphExecUpdate` calls in the whole capture, against 11,588 replays.

## Findings

1. **About a quarter of each step is GPU idle time on the CPU side.** 567 µs of gap against 1,601 µs of replay, a 2.17 ms step. Halving the gap would make steps about 15% faster. This is the biggest target the capture shows.

2. **The gap is many small, serial CPU–GPU round trips.** Each step waits about 27 times and makes about 10 tiny copies (4–40 bytes, plus 20 KB vectors). Each *copy, then wait* pair leaves the GPU idle until the CPU issues more work. The sizes fit speculative-decoding bookkeeping: 20,480 B is one 5,120-wide float32 hidden state, 102,400 B is five of them, and 40 B is ten int32 values, such as token ids. **To confirm, this needs CPU call stacks.**

3. **Each MTP check copies all of its logits to the CPU.** 4,966,400 B = 5 positions × 248,320 × 4 bytes. That's the 4 drafted tokens plus one, matching `spec-draft-n-max = 4` and the `mul_mat_vec_q<…, 5>` kernels, times a float32 row per position. The copy is cheap (about 0.2 ms each, 143 ms of copies in 23 s). Sampling over 1.2 M logits on the CPU every check may not be. Same caveat: the capture recorded no CPU samples.

4. **Small kernels run outside the graph every step.** About 6.5 kernels per replay run outside the CUDA graph (0.27 s of GPU time in the window). Each one costs a separate launch. They are probably the draft and acceptance steps, which have their own shapes.

5. **Most GPU time can't be broken down yet.** 59.8 of the 69.1 busy seconds are opaque graph replays. The kernel table below is only kernels launched outside graphs: prompt processing and the small per-step kernels.

## CPU samples are missing

This run was made with the backend elevated and **CPU call stacks** on. The report confirms that the app asked for sampling: its capture settings include `CAPTURE_EVENT_TYPE = CpuCycles`, `RATE_HZ = 1000` and thread backtraces. None of those appear in a non-elevated capture, where the app passes `--sample=none`. Even so, the report holds no CPU samples and no thread-activity (context switch) events, and nsys logged no warning or error about either.

Both come from the same Windows kernel event tracing (ETW) session, so that session delivered nothing. The cause isn't known yet. Candidates:

- CPU sampling not working in nsys's `launch` / `start` session mode on Windows, which is the mode the app used so it could write the report before the router stops;
- another tool holding the kernel trace session;
- virtualisation-based security or Hyper-V (Docker Desktop is installed) limiting kernel sampling.

**Resolved: it was the first.** `scripts\profiling\check-cpu-sampling.ps1`, run elevated on the same machine, profiled CPU-bound Python in each way the app could drive nsys:

| Mode | CPU samples | Thread events |
|---|---|---|
| `nsys profile` | 176,291 | 252,760 |
| `nsys launch`, then `start` / `stop` (what the app used) | **0** | **0** |
| `nsys profile --session-new`, ended with `nsys stop` | 53,107 | 73,056 |
| `nsys profile --session-new --start-later`, two `start` / `stop` captures, sampling options on `profile` | 29,158 / 23,381 | 40,154 / 35,276 |
| The same, sampling options on `start` | 27,656 / 23,944 | 37,684 / 34,873 |

In `--start-later` mode the program kept running after the first stop. So the app now starts the router under `nsys profile --session-new --start-later` with the sampling options. Captures still start and stop with `nsys start` / `nsys stop`, and the report is still written before the router stops.

One nsys quirk: in this mode the first capture's report goes to the `--output` given to `nsys profile`, not to `nsys start`. The app points that at a placeholder in `captures\.pending` and moves the report to its proper name after the stop.

The GPU side matches run 1: busy 87–89% during generation, graph replay median **1,613 µs**, gap after it median **647 µs**. The gap is slightly longer than run 1's 567 µs, probably the cost of sampling every thread. Per replay there are 30 waits and 10.7 copies, with the same sizes as run 1.

### Where the decode thread's time goes

Windows samples the whole machine; 669,409 of the 5.3 M samples are in llama-server, and **61% of those are one thread**: the model process's main thread (process 20484, thread 4144), which runs `server_queue::start_loop` → `update_slots`. The router process and the HTTP threads (5%) are minor.

That thread's samples, by call path:

| Share of thread | Call path |
|---|---|
| 43.9% | `update_slots` → `server_context_impl::decode` (the verify decode) |
| 28.8% | … → `llama_context::synchronize`: waiting for the GPU to finish the decode |
| 7.1% | … → `llama_context::decode`: building, uploading inputs and launching it |
| 3.6% | … → `common_speculative_process` (MTP state update after verify) |
| 23.8% | `update_slots` → `server_context_impl::pre_decode` |
| **19.1%** | … → `common_speculative_impl_draft_mtp::draft`: **MTP drafting** |
| 11.7% | … → `llama_context::decode` of the MTP head; only 2.6% is the graph running (`ggml_backend_cuda_graph_compute`), **8.5% is `ggml_backend_sched_copy_input`** |
| 7.3% | … → `common_sampler_sample` → `llama_context::synchronize`: waiting to sample each draft token |
| 3.8% | `update_slots` → `iterate`: sampling and accepting tokens (1.1%), sending the streamed response (0.8%) |

Across both decodes, **`ggml_backend_sched_copy_input` is 14.5% of the thread**. It goes `ggml_backend_tensor_copy` → `ggml_backend_tensor_set` → `ggml_backend_cuda_buffer_set_tensor` → `cudaMemcpyAsync`, with 13.8% inside `cudaMemcpyAsync` itself. These are the scheduler copying graph inputs held in host memory to the GPU. The 20 KB, 100 KB, 40 B and 8 B host-to-device copies in the step tables match MTP hidden states, token ids and positions.

68% of the thread's samples end in the Windows kernel and 27% in the CUDA driver (`nvcuda64.dll`). The thread is spin-waiting most of the time it waits. That costs a CPU core but isn't the bottleneck.

### Findings from run 2

6. **MTP drafting is the largest CPU-side cost in the step: 19.1% of the decode thread.** Drafting is sequential. Each draft token is a small MTP-head decode, then a wait, then a CPU sample before the next draft can start. The GPU has little to do during it: the MTP head's graph is only 2.6% of the thread. This is where most of the 0.57–0.65 ms gap comes from, and it confirms findings 2 and 3.

7. **Uploading graph inputs blocks the decode thread: 14.5% of it, inside `cudaMemcpyAsync`.** A plausible cause, not yet verified: the inputs sit in ordinary (pageable) host memory, from which CUDA can't copy asynchronously. The thread then can't prepare the next graph while the GPU finishes the current one. The fix to try is to keep the scheduler's input buffers in pinned memory, so the copies are truly asynchronous.

8. **Sampling itself is cheap.** `common_sampler::set_logits` plus `std::partial_sort` (top-k) are about 1% of the thread, even with 5 × 248 k logits per check. The 5 MB logits copy (finding 3) isn't a CPU problem.

### What to try

These are llama.cpp changes, measured with a debug-symbol build and the same benchmark:

- **Pinned input buffers** for `ggml_backend_sched_copy_input` on CUDA (finding 7). Look at how the scheduler allocates its input copies, and whether `GGML_CUDA` has a host-buffer option for them.
- **Fewer round trips per MTP draft** (finding 6): sample the draft token on the GPU (argmax) instead of copying logits back, or run consecutive draft steps without syncing in between.
- **For comparison,** the same benchmark with MTP off (`spec-type` unset), and with `spec-draft-n-max` 2 instead of 4. They show how tokens/s trades against the drafting cost.
